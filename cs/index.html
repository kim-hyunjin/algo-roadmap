01.1데이터 표현비트 · 정수 · 문자 · 부동소수점열기
핵심 원리

컴퓨터의 모든 값은 유한한 비트 패턴입니다. 표현 범위와 정밀도에 한계가 있다는 사실이 오버플로, 인코딩 오류, 0.1 + 0.2 문제의 출발점입니다.

AI 시대의 연결점

모델의 FP32·FP16·INT8 양자화가 정확도와 메모리, 속도를 어떻게 바꾸는지 이해하는 토대입니다.

스스로 답할 질문
  • signed 정수는 음수를 어떻게 표현할까?
  • UTF-8에서 한 글자의 크기가 다른 이유는?
  • 부동소수점 비교에 오차 허용값이 필요한 이유는?
실습하기

브라우저 콘솔에서 Number.MAX_SAFE_INTEGER와 0.1 + 0.2를 확인하고 결과를 설명해보세요.

스스로 답할 질문의 정답
  1. 1

    일반적으로 최상위 비트에 부호를 따로 두지 않고 2의 보수로 표현해 덧셈 회로를 그대로 사용할 수 있게 합니다.

  2. 2

    UTF-8은 하나의 유니코드 스칼라 값을 1~4바이트로 인코딩합니다. 사용자가 한 글자로 보는 문자열은 여러 코드 포인트로 이루어져 4바이트보다 클 수 있습니다.

  3. 3

    대부분의 10진 소수는 이진수로 정확히 표현할 수 없어 반올림 오차가 생깁니다. 값의 크기에 맞춘 상대·절대 허용 오차나 정확한 decimal 연산이 필요한지도 함께 판단해야 합니다.

AI 시대의 연결점

GPU가 병렬 계산에 강한 이유와 모델 로딩·추론에서 메모리가 병목이 되는 이유를 판단할 수 있습니다.

스스로 답할 질문
  • CPU 캐시는 왜 필요한가?
  • 연속된 배열 순회가 임의 접근보다 빠른 이유는?
  • CPU와 GPU의 강점은 어떻게 다른가?
실습하기

큰 배열의 순차 접근과 미리 만든 인덱스 순서의 무작위 접근을 여러 번 측정하세요. JIT 워밍업 뒤 같은 반복 횟수를 쓰고, 난수 생성 시간은 측정 구간에서 제외하세요.

스스로 답할 질문의 정답
  1. 1

    CPU와 RAM의 큰 속도 차이를 줄이기 위해 자주 쓰거나 곧 쓸 데이터를 더 빠른 캐시에 보관합니다.

  2. 2

    연속 접근은 한 번 가져온 캐시 라인의 주변 데이터를 재사용하고 하드웨어 선읽기도 활용할 수 있기 때문입니다.

  3. 3

    CPU는 복잡한 제어와 낮은 지연에, GPU는 같은 연산을 많은 데이터에 적용하는 대규모 병렬 처리에 강합니다.

01.3복잡도와 확장성시간 · 공간 · 상수 비용열기
핵심 원리

복잡도는 입력 크기가 커질 때 자원 사용량이 어떻게 증가하는지 설명하는 언어입니다. Big-O와 실제 상수 비용을 함께 보고, 최악·평균·분할상환 중 어떤 비용을 말하는지와 입력 분포를 구분해야 합니다.

AI 시대의 연결점

AI가 제안한 코드가 작은 예제만 통과하는지, 실제 트래픽과 데이터 크기에서도 버틸지 검증하는 최소 기준입니다.

스스로 답할 질문
  • O(n log n)과 O(n²)의 차이는 언제 체감될까?
  • 시간을 줄이기 위해 공간을 쓰는 사례는?
  • Big-O가 같아도 속도가 다른 이유는?
실습하기

중복 탐색 코드를 Set을 쓰는 방식으로 바꾸고 입력 크기별 시간을 비교해보세요.

스스로 답할 질문의 정답
  1. 1

    입력이 커질수록 증가율 차이가 급격히 벌어지므로, 작은 입력에서는 비슷해도 수만~수백만 건에서 크게 체감됩니다.

  2. 2

    해시 테이블에 값을 저장해 반복 탐색을 한 번의 조회로 바꾸거나 계산 결과를 메모이제이션하는 경우가 대표적입니다.

  3. 3

    Big-O는 증가율만 나타내며 상수 계수, 캐시 효율, 언어·런타임, 실제 입력 특성은 생략하기 때문입니다.

운영체제와 동시성

02.1프로세스와 스레드격리 · 공유 · 문맥 교환열기
핵심 원리

프로세스는 독립된 주소 공간을 가지며, 스레드는 한 프로세스의 메모리를 공유합니다. 격리는 안전성을, 공유는 효율을 주지만 동기화 비용을 만듭니다.

AI 시대의 연결점

AI 서버의 worker 수, 병렬 요청 처리, Python 멀티프로세싱 선택을 이해하는 데 직접 연결됩니다.

스스로 답할 질문
  • 프로세스와 스레드는 무엇을 공유할까?
  • 문맥 교환에는 왜 비용이 드는가?
  • 동시성과 병렬성은 어떻게 다른가?
실습하기

작업 관리자에서 브라우저의 프로세스·스레드 수와 메모리 사용량을 관찰해보세요.

스스로 답할 질문의 정답
  1. 1

    프로세스끼리는 기본적으로 주소 공간이 분리되지만 IPC나 공유 메모리를 명시적으로 사용할 수 있습니다. 같은 프로세스의 스레드는 코드·힙·파일 같은 자원을 공유하되 각자 스택과 레지스터 상태를 가집니다.

  2. 2

    실행 상태를 저장·복원하고 스케줄러가 개입하며 캐시와 TLB의 유효한 데이터가 줄어들 수 있기 때문입니다.

  3. 3

    동시성은 여러 작업이 겹치는 시간에 진전하도록 구성하는 것이고, 병렬성은 여러 작업을 실제로 동시에 실행하는 것입니다. 실제 선택은 CPU/I/O 비중과 언어 런타임 제약도 함께 봅니다.

02.2동기화와 교착상태race condition · lock · atomic열기
핵심 원리

공유 상태를 동시에 바꾸면 실행 순서에 따라 결과가 달라집니다. 잠금은 이를 막지만 잘못 사용하면 대기와 교착상태를 일으킵니다. 원자 연산은 한 연산의 쪼개짐을 막지만 여러 값에 걸친 복합 불변식까지 자동으로 보호하지는 않습니다.

AI 시대의 연결점

에이전트 여러 개가 같은 파일이나 DB 행을 수정할 때 생기는 덮어쓰기와 중복 실행을 예방할 수 있습니다.

스스로 답할 질문
  • race condition은 왜 재현하기 어려운가?
  • 임계 구역은 무엇인가?
  • 교착상태의 네 조건은 무엇인가?
실습하기

스레드를 지원하는 언어 런타임에서 공유 카운터를 여러 작업이 갱신하게 만들고, 잠금·원자 연산 적용 전후를 비교하세요. 브라우저 메인 스레드만으로는 같은 race를 재현하기 어렵습니다.

스스로 답할 질문의 정답
  1. 1

    스레드 스케줄링과 실행 타이밍에 따라 연산 순서가 달라져 같은 입력에서도 간헐적으로만 나타나기 때문입니다.

  2. 2

    둘 이상의 실행 흐름이 동시에 접근하면 결과가 깨질 수 있어 한 번에 하나만 실행하도록 보호해야 하는 코드 구역입니다.

  3. 3

    상호 배제, 점유하며 대기, 비선점, 순환 대기가 동시에 성립하는 것입니다.

02.3가상 메모리와 I/Ostack · heap · page · buffer열기
핵심 원리

가상 메모리는 각 프로세스에 독립된 주소 공간을 제공하고, 운영체제는 페이지 단위로 실제 메모리를 관리합니다. I/O는 버퍼와 캐시를 통해 느린 장치의 비용을 숨깁니다.

AI 시대의 연결점

OOM, 메모리 누수, 대용량 파일 스트리밍, 모델 적재 실패를 진단하는 공통 언어가 됩니다.

스스로 답할 질문
  • stack과 heap의 수명은 어떻게 다른가?
  • 페이지 폴트는 언제 발생하는가?
  • 파일 전체 읽기와 스트리밍의 차이는?
실습하기

큰 파일을 한 번에 읽는 코드와 줄 단위 스트리밍 코드의 메모리를 비교하세요.

스스로 답할 질문의 정답
  1. 1

    스택 데이터는 보통 함수 호출 범위에 따라 자동으로 생성·해제되고, 힙 데이터는 동적으로 할당되어 명시적 해제나 가비지 컬렉션까지 살아 있습니다. 다만 closure, escape analysis, 언어 런타임에 따라 실제 배치는 달라질 수 있습니다.

  2. 2

    프로세스가 접근한 가상 메모리 페이지가 현재 물리 메모리에 없거나 접근 권한이 맞지 않을 때 발생합니다.

  3. 3

    전체 읽기는 파일 크기만큼 메모리를 점유하지만 스트리밍은 작은 조각씩 처리해 메모리 사용량을 제한합니다.

03.1네트워크 계층IP · TCP/UDP · port열기
핵심 원리

IP는 목적지까지 패킷을 전달하고, TCP는 순서와 재전송으로 신뢰성을 더합니다. 포트는 한 호스트 안에서 요청이 도착할 프로그램을 구분합니다.

AI 시대의 연결점

모델 API 타임아웃, 스트리밍 끊김, 방화벽 문제를 애플리케이션 코드와 분리해 볼 수 있습니다.

스스로 답할 질문
  • IP와 포트의 역할은 어떻게 다른가?
  • TCP 연결에는 왜 왕복 시간이 필요한가?
  • UDP가 유리한 상황은?
실습하기

ping과 netstat으로 도달성과 열린 연결을 관찰하고, Windows의 tracert 또는 Unix 계열의 traceroute로 경로를 확인하세요. ICMP가 차단된 ping 실패만으로 TCP·HTTP 서비스 장애를 단정하지 마세요.

스스로 답할 질문의 정답
  1. 1

    IP 주소는 네트워크에서 호스트를 찾고, 포트 번호는 그 호스트 안에서 통신할 애플리케이션을 구분합니다.

  2. 2

    양쪽이 초기 순서 번호와 통신 가능 여부를 확인하는 핸드셰이크를 주고받아야 하기 때문입니다.

  3. 3

    일부 손실을 허용하면서 지연을 줄여야 하는 실시간 음성·영상, 게임, DNS 조회 등에 유리합니다.

03.2웹 요청의 생애DNS · TLS · HTTP · status열기
핵심 원리

DNS로 서버를 찾은 뒤 HTTP/1.1·2는 일반적으로 TCP 연결과 TLS 협상을 거치고, HTTP/3는 QUIC 연결 안에서 보안과 전송을 구성합니다. 이후 HTTP 요청과 응답이 오가며 상태 코드와 헤더가 그 계약을 표현합니다.

AI 시대의 연결점

LLM API의 인증, rate limit, SSE 스트리밍, 캐시 헤더를 정확히 다룰 수 있습니다.

스스로 답할 질문
  • HTTPS는 무엇을 보호하는가?
  • GET과 POST의 의미 차이는?

    저장소·로그·배포 산출물에 노출되기 쉽고 유출 뒤 회수와 교체도 어려우므로 환경별 비밀 관리와 주기적인 교체가 필요합니다. 로그와 오류 메시지에서도 마스킹해야 합니다.

  3. 3

    신뢰 수준이 바뀌는 모든 경계에서 검증합니다. 다만 검증만으로 충분하지 않으므로 SQL은 파라미터화하고 HTML은 출력 위치에 맞게 인코딩하며, 파일·도구 실행은 허용 목록과 권한 검사를 추가합니다.

06.2AI 애플리케이션 구조token · embedding · RAG · tool열기
핵심 원리

AI 앱은 모델 하나가 아니라 입력 정제, 검색, 프롬프트, 추론, 도구 실행, 출력 검증이 이어지는 파이프라인입니다. 각 단계는 서로 다른 실패 방식을 가집니다.

AI 시대의 연결점

모델 탓으로 뭉뚱그리지 않고 검색 품질, 컨텍스트, 도구, 후처리 중 실제 원인을 분리할 수 있습니다.

스스로 답할 질문
  • 토큰 제한은 입력 설계에 어떤 영향을 주는가?
  • 임베딩 검색은 키워드 검색과 어떻게 다른가?
  • 도구 실행 결과는 왜 다시 검증해야 하는가?
실습하기

질문 → 검색 → 프롬프트 → 모델 → 검증의 흐름도를 그리고 단계별 실패를 하나씩 적으세요.

스스로 답할 질문의 정답
  1. 1

    질문·지침·검색 문서·출력이 컨텍스트 한도를 나눠 쓰므로 관련성이 높은 정보만 선택하고 길이를 관리해야 합니다.

  2. 2

    키워드 검색은 정확한 용어에, 임베딩 검색은 의미적 유사성에 강점이 있습니다. 둘을 결합한 hybrid search와 reranking으로 약점을 보완할 수 있습니다.

  3. 3

    도구도 실패하거나 오래된·악의적인 데이터를 반환할 수 있습니다. 도구 결과와 모델 출력은 명령이 아니라 신뢰하지 않는 데이터로 취급하고 스키마·권한·대상 범위를 실행 직전에 다시 검증해야 합니다.

06.3평가와 안전한 운영eval · guardrail · cost · latency열기
핵심 원리

확률적 출력은 단일 정답 테스트만으로 평가하기 어렵습니다. 대표 데이터셋, 품질 기준, 비용·지연, 실패 사례를 함께 측정하고 사람의 확인이 필요한 경계를 정해야 합니다. 전체 평균뿐 아니라 언어·난이도·사용자·위험 수준별 slice와 평가 데이터 오염도 확인합니다.

AI 시대의 연결점

데모가 잘 되는지보다 실제 사용자에게 일관되고 안전한 가치를 주는지 판단하는 기준입니다.

스스로 답할 질문
  • 오프라인 평가와 온라인 지표는 어떻게 다른가?
  • 정확도 외에 무엇을 측정해야 하는가?
  • 사람의 승인이 필요한 작업은 무엇인가?
실습하기

실제 질문 20개를 언어·난이도·위험 수준별로 나누고 기대 기준을 만드세요. 모델 변경 전후의 품질·비용·지연과 slice별 실패를 비교하고 평가자 판단이 엇갈린 항목도 기록하세요.

스스로 답할 질문의 정답
  1. 1

    오프라인 평가는 고정된 데이터셋으로 출시 전 품질을 반복 비교하고, 온라인 지표는 실제 사용자 환경의 행동·성공률·장애를 관찰합니다. 평가셋이 학습·프롬프트 조정에 과도하게 노출되지 않게 분리해야 합니다.

  2. 2

    안전성, 일관성, 근거성, 비용, 지연 시간, 실패율과 사용자 만족도를 측정하고 전체 평균과 중요한 slice를 함께 봅니다. 사람 평가를 쓰면 평가자 간 일치도도 확인합니다.

  3. 3

    되돌리기 어렵거나 금전·법률·안전·개인정보에 큰 영향을 주는 고위험 작업에는 실행 전 사람의 승인이 필요합니다.

9-week field guide

시간 비중은 읽기 30%,
실습 60%, 설명 10%

하루 60~90분, 주 3회를 기준으로 합니다. 세 번째 학습일에는 이전 주 내용을 3분 설명한 뒤 새 실습을 시작합니다.

  1. W01
    데이터 표현 + 복잡도

    숫자 실험과 배열 성능 측정

    완료: 결과 차이를 3분 설명하고 측정 기록을 남깁니다.
  2. W02
    CPU + 프로세스·스레드

    프로세스 관찰과 실행 방식 비교

    완료: CPU·I/O 작업의 실행 방식을 근거와 함께 고릅니다.
  3. W03
    동시성 + 메모리·I/O

    race condition 재현과 스트리밍

    완료: 잠금 전후 결과와 파일 읽기 메모리를 측정합니다.
  4. W04
    네트워크 + 웹 + 실패

    한 API 요청의 전 구간과 재시도 추적

    완료: timeout·jitter·중복 방지 정책을 포함한 호출 흐름을 그립니다.
  5. W05
    SQL + 인덱스

    작은 스키마와 쿼리 플랜 분석

    완료: 인덱스 전후 플랜과 join 행 수를 비교합니다.
  6. W06
    트랜잭션 + 캐시

    부분 실패와 오래된 데이터 실험

    완료: 트랜잭션 경계와 캐시 무효화 정책을 문서화합니다.
  7. W07
    설계 + 테스트

    AI 생성 코드의 계약과 테스트 작성

    완료: 정상·경계·오류·불변식 테스트가 있는 작은 모듈을 만듭니다.
  8. W08
    관측성 + 보안

    요청 추적과 역할별 권한표 작성

    완료: 민감정보 없는 로그와 거부되어야 할 요청 목록을 만듭니다.
  9. W09
    AI 파이프라인 + 평가

    검색·도구 경계와 slice별 평가셋 완성

    완료: 품질·비용·지연·안전 기준과 롤백 조건을 수치로 정합니다.
